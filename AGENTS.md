# Инструкции для ИИ-агентов (Claude Code, Codex, Cursor и др.)

Этот файл читается агентом в начале работы с репозиторием. Здесь все, что нужно знать, чтобы вносить изменения и ничего не сломать.

## Что это за проект

«Деканат Next»: рабочий прототип личного кабинета студента для номинации «Вайб-кодинг» конкурса MGIMO AI Challenge (задание «Цифровой деканат будущего»). Кабинет адаптирован под структуру Университета ИТМО, но это концепт, а не официальный сервис. Все данные вымышлены.

Обязательное ядро из задания (не удалять и не ломать):
1. Вход и профиль (ФИО, факультет, направление, курс, группа).
2. Расписание на сегодня и на неделю, аудитория и преподаватель, переносы и отмены.
3. Успеваемость: баллы и зачеты, сессия, общая картина.
4. Заявки и справки онлайн со статусом.
5. Уведомления: объявления деканата, дедлайны, изменения.

Дополнительно: кабинет сотрудника деканата, переписка с деканатом, электронная справка с QR-кодом, калькулятор баллов, выгрузка расписания в календарь, темная тема, установка на телефон (PWA).

## Стек и запуск

- Python 3.12-3.14, FastAPI, Jinja2 (серверный рендеринг), SQLAlchemy 2, SQLite. Для PostgreSQL нужно поставить драйвер `psycopg` и задать `DATABASE_URL`, на PostgreSQL прототип не проверялся. Счетчики входа, лимит проверок пароля и блокировка сброса демо живут в памяти процесса: прототип рассчитан на один процесс.
- Рабочие зависимости (`requirements.txt`) закреплены на версиях без известных уязвимостей на 22 ноября 2026 (проверка `pip-audit -r requirements.txt`).
- Пароли: argon2id (`argon2-cffi`). QR: `qrcode` (SVG).
- Фронтенд без сборки: `app/static/css/app.css`, `app/static/js/app.js`. Шрифты Unbounded и Golos Text лежат локально.

```bash
pip install -r requirements.txt -r requirements-dev.txt
uvicorn app.main:app --reload          # http://127.0.0.1:8000
python -m pytest -q                    # все тесты должны проходить
python -m app.seed --reset             # пересоздать демо-базу
```

## Правила, которые нельзя нарушать

1. **Студент видит только свои данные.** Идентификатор студента берется только из серверной сессии (`require_student`), никогда из адреса или формы. Любой запрос к данным студента фильтруется по `student_id` текущего пользователя. Чужая запись: ответ 404, а не 403. Номер записи в адресе объявляется как `IdPath` (`routes/common.py`): неверный или огромный номер тоже дает 404.
2. **Каждый POST внутри кабинета проверяет CSRF-токен** (`check_csrf`) и роль (`require_student` / `require_staff`). У формы входа сеанса еще нет, ее защищает проверка Origin в `main.py` (схема, имя и порт). Пользователя с другой ролью GET-запрос перенаправляет в его кабинет, POST получает 403.
3. **Пароли только в виде хеша argon2id.** Токен сеанса в базе только как SHA-256. Хешировать и проверять пароль только через `hash_password` и `verify_password`: они ограничивают число одновременных проверок (по 64 МБ каждая).
4. **Никаких секретов в репозитории.** Ключи и пароли сервисов только через переменные окружения. Тест `test_no_secrets_in_repository` это проверяет.
5. **Только вымышленные данные.** Не добавлять реальные ФИО, оценки, номера зачеток. Не подключаться к системам вуза.
6. **Не использовать логотип вуза.** На страницах должно быть видно, что это концепт для конкурса.
7. **Время.** "Сейчас" и расписание считаются в часовом поясе вуза (`services/timeutil.py`). Служебные отметки в базе хранятся в UTC. Текущее время брать только через `timeutil.now_local()`, `today()` и `utcnow()`: тесты подменяют его через `timeutil.freeze()`. Проверки «в прошлом или нет» сравнивают время начала пары (`schedule.lesson_start`), а не только дату.
8. **Шкала баллов** взята из открытого документа ИТМО (edu.itmo.ru/files/23) и закреплена тестом `test_grade_scale_matches_itmo_document`.
9. **Демо-режим.** Тестовые аккаунты (`User.is_demo`) общие для всего жюри: в них нельзя менять пароль, блокировка входа идет по паре «логин + IP», а база пересоздается каждый день и после 30 минут без активности с сохранением открытых сеансов (`ensure_demo_fresh` в `seed.py`). Активность: только запросы с cookie сеанса, отметка хранится в базе (`Meta.last_activity`). Сброс стирает строки и создает данные заново в одной транзакции; таблицы при сбросе не удалять. Демо-данные попадают только на рабочие дни и в рабочие часы и строятся из реальных событий: уведомление об изменении расписания создается из самого изменения (`schedule.change_notice`). Это проверяет `tests/test_time_machine.py`. Переключение «студент / деканат» (`/demo/switch`) работает только между демо-аккаунтами.
10. **Заявки.** Статусы и подписи зависят от вида заявки (`services/catalog.py`): справка, документ, заявление. Код проверки по QR есть только у электронных справок. Электронная справка об обучении выдается сразу, без сотрудника (`INSTANT_TYPES`).
11. **Учебный календарь** (`config.py`): начало и конец занятий, праздники. После конца занятий в расписании показывается сессия.
12. **Адрес клиента и схема** (`client_ip`, `is_https` в `security.py`, `_allowed_hosts` в `main.py`): X-Forwarded-For, X-Forwarded-Proto и X-Forwarded-Host учитываются только от внутреннего адреса прокси. Абсолютные ссылки (QR-код) строятся через `public_base_url`.

## Стиль интерфейса

- Тексты на русском, простые и конкретные, без буквы «ё» и без длинного тире.
- Мобильная версия первая: все сценарии должны работать на ширине 360 px.
- Пользовательский текст бывает очень длинным (ссылка без пробелов). Сетки и строки, где он выводится, задаются как `minmax(0, 1fr)` или с `min-width: 0`, иначе длинное слово раздвигает страницу. `overflow-wrap: anywhere` глобально не ставить: он рвет обычные слова в узких местах (время на табло, подписи меню).
- Версия оформления (`ASSET_VERSION` в `web.py`) считается по содержимому CSS и JS, сервис-воркер получает ее автоматически. Вручную ничего поднимать не нужно.
- CSP запрещает inline-скрипты и inline-стили: JS только в `app/static/js/`, стили только в `app.css`. Ширины полос задаются атрибутами SVG.
- Цвета и размеры через CSS-переменные в начале `app.css`, есть светлая и темная тема.
- Иконки: `{{ icon('имя') }}` из `static/icons/sprite.svg`.

## Как вносить изменения

1. Прочитать затрагиваемые файлы целиком.
2. Для ошибки: сначала тест, который ее воспроизводит, потом исправление. Потом найти тот же шаблон в других местах кода и исправить везде, а не в одном месте (главный вывод третьей проверки: точечные исправления оставляли ту же ошибку рядом).
3. Запустить `python -m pytest -q`. Тесты проверяют целые классы ошибок, и новая страница или форма попадает в них автоматически:
   - `test_crawl.py`: страницы, достижимые по ссылкам, под каждой ролью без ошибок сервера, плюс pyflakes;
   - `test_forms_fuzz.py`: найденные формы со «злыми» значениями без ошибок сервера, выбор пользователя сохраняется после ошибки (обход ограничен, см. PROCESS.md, разделы 11 и 12);
   - `test_time_machine.py`: 14 моментов учебного года, инварианты демо-данных;
   - `test_layout.py`: Chromium на 360 px с длинным текстом, без прокрутки и ошибок консоли, и отдельно табло (overflow: hidden прячет обрезку, поэтому проверяются элементы табло, включая строку изменения и подсказки) в моменты с «Онлайн», «Спортзал», длинной аудиторией и длинной фамилией на замене на 360, 390 и 1440 px (нужен `python -m playwright install chromium`).
4. Проверить страницу на ширине 360, 390 и 1440 px, в светлой и темной теме.
5. Обновить `docs/PROCESS.md`, если изменение заметное.
